# blind-tdd (Claude Code plugin)

A test-first gate, enforced rather than requested: a fresh agent writes the
acceptance tests from the spec **alone** — a `PreToolUse` hook blocks every read
of the implementation — the implementer makes those tests pass without being able
to edit them, a blind runner verifies green against hash-sealed tests, and an
arbiter rules on any challenge. Independence is a permission, not a policy.

This plugin is the **blindness layer** (hooks + agent definitions) for use inside
any Claude Code project. The orchestration **engine** — the red/green sealing,
coverage check, and challenge/arbiter flow — is the standalone
**[Themis](https://github.com/dscherm/themis)** package, installed via pip and
**never vendored** into this plugin. The plugin enforces blindness; Themis drives
the cycle.

## 60-second quickstart

```bash
# 1. Add the Themis marketplace and install the plugin
/plugin marketplace add dscherm/themis
/plugin install blind-tdd@themis

# 2. Install the orchestration engine (Themis) into your project's environment
pip install -r requirements.txt        # themis-blind-tdd @ git+https://github.com/dscherm/themis.git

# 3. Describe your public surface so the blind writer has something to test against
#    (one file, the ONLY thing the writer may read beyond the task spec)
$EDITOR public_api.md

# 4. Run a blind cycle — the hooks are already live (passthrough until a session opens)
python -m blind_tdd.gate_integration   # or drive it from your harness; see Themis docs
```

The hooks auto-activate on install and are **passthrough-by-default**: with no
`.themis/blind_tdd/active_session.json` present they allow every tool call, so the
plugin is safe to leave always-on. They start enforcing only once the engine opens
a blind session.

## What's here

| Path | Role |
|---|---|
| `.claude-plugin/plugin.json` | Plugin manifest. Hooks are auto-discovered from `hooks/hooks.json`. |
| (repo root) `.claude-plugin/marketplace.json` | The Themis marketplace that lists this plugin for `/plugin install`. |
| `hooks/hooks.json` | PreToolUse path-guard (file reads) + PreToolUse bash-guard (shell) + PostToolUse audit, via `${CLAUDE_PLUGIN_ROOT}`. Auto-activates; passthrough-by-default. |
| `hooks/blind_tdd_{path_guard,bash_guard,audit}.py` | The enforcement hooks. Pure stdlib — they read the active-session file and allow/deny; they do **not** import the engine. |
| `agents/blind-{writer,runner,arbiter}.md` | Generated subagent defs (frontmatter + canonical prompt body) — see `assemble.py`. |
| `commands/{setup,security-pack-setup}.md` | Setup interviews (see below). |
| `requirements.txt` | The Themis engine pin (generated by `assemble.py`). |
| `LICENSE` | MIT. |

### Bash guard (closes the in-session runner hole)

The path-guard hook does not guard `Bash` (by design). The bash-guard does:
while a blind session is active it denies `Bash` for writer/arbiter entirely, and
for the runner allows **only** test-runner commands (pytest, npm test, dotnet
test, …) — blocking `cat`/`grep`/`find`, chained reads (`pytest && cat src`), and
command substitution. Passthrough when no session is active.

### Setup commands

Two interviews, both run once by a human — deliberately, because their output
is policy the implementing agent must not control:

- **`/blind-tdd:setup`** — routing: which tasks the (expensive) gate engages
  on. Writes `gate.blind_tdd.routing` via `python -m blind_tdd.init`.
- **`/blind-tdd:security-pack-setup`** — tailors the security AC pack to the
  project's actual attack surface. Explores the repo first, interviews one
  question at a time against the evidence found, drafts concrete criteria,
  and loops `python -m blind_tdd.pack_wizard --lint` as an objective exit
  gate before a human-approved install.

## Spawner design — in-session subagents

A plugin `PreToolUse` hook fires on **and blocks** tool calls made by `Agent`-tool
subagents, not just the main session (confirmed 2026-06-08). So the blind
writer/runner/arbiter run as **in-session subagents**: the engine toggles
`active_session.json` and stages the brief, the orchestrating model spawns the
subagent via the `Agent` tool, and the always-on hook enforces blindness — no
`claude -p` subprocess and no settings save/restore dance. Themis keeps a headless
`claude -p` spawner as a CI fallback.

## Engine, via pip — not vendored

`assemble.py` generates the agent defs (from `templates/blind_tdd/prompts/`),
copies the hook scripts (from `templates/hooks/`), and writes `requirements.txt`
with the Themis pin. It does **not** copy any engine source into the plugin: the
orchestration lives in the `themis-blind-tdd` distribution and resolves through a
normal `import blind_tdd`. `test_plugin_smoke.py` enforces this — it fails if any
engine module is vendored in or if the engine cannot be imported from the
installed package.

Re-generate after editing a prompt or hook:

```bash
python plugin/blind-tdd/assemble.py
python -m pytest plugin/blind-tdd/ -q
```

## Demo

A deterministic, self-contained demo drives the **real shipped hooks** through
all four beats — blocked read → red+seal → green → seal/lock catches tampering:

```bash
bash plugin/blind-tdd/demo/run.sh                     # run it (scratch dir, self-cleaning)
asciinema play plugin/blind-tdd/demo/demo.cast        # watch the recording
```

See [`demo/README.md`](./demo/README.md) for the transcript, how to regenerate
the cast, and how to convert it to a GIF.
