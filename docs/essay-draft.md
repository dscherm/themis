# Backpressure the Agent Can't Route Around

*A check the agent can read and edit is one the optimizer routes around when that's cheaper than the work — producing false greens exactly where the code is wrong. Here's what enforced, independent backpressure takes.*

You've built the harness you wanted: an agent that turns a spec into working code, with type checks, a linter, and a test suite in the loop, returning each failure before it reaches you. Most of the time it converges, the checks pass, the output looks right.

Yet, dangerous and invisible failures slip through, because the gate intended to catch failures was shaped BY the code instead of shaped to TEST it. Why? Reward hacking is structural: an agent optimizes whatever signal stands in for success, by the cheapest path. When the same agent writes the code and its check, the check isn't an independent measurement. It's a mirror — it inherits the code's misreadings and confirms them. Misread the spec, and the code is wrong and the test that certifies it is wrong the same way. The suite is green; nothing was constrained; no failure reaches the loop, because from inside it there was nothing to report.

The usual fix is to assign a second agent the verifier role, and for most work that's right. But look at where the verifier sits: a role in a prompt, with the same access as everything else. It can read the implementation; the tests can be edited after the fact. The separation lives in the instructions, not the system — backpressure the agent can reach in and relieve. And it will, not from malice but from gradient: a constraint it can perceive and act on is terrain it routes around the moment that's cheaper than the work. **Backpressure you ask the agent to honor is a policy; backpressure it cannot route around is a mechanism. Policies erode under optimization pressure; mechanisms don't.** A check that pushes back needs its independence to be a capability the agent is denied, not a behavior it's asked to perform. The tuned in-between layers — semantic evals, model reviewers, mutation testing — are good and usually enough, but each is only as trustworthy as your tuning; enforced blindness differs in kind, because you don't trust the judge to judge well, you remove its ability to see the answer.

## The architecture

I built a gate to test the idea, called Themis. The whole design is permissions — each agent gets exactly what it needs and is denied the rest, enforced by tooling, not instruction.

A **blind writer** derives the tests from the spec; a hook denies it any read of the source, so it cannot teach to the test. An **implementer** then writes code to pass them, free to change everything but the sealed tests. The wall is honest about its limit: a path guard blocks the edit tools from rewriting a locked test but doesn't cover the shell — so before any code exists, each test file is fingerprinted (SHA-256) and re-checked at the end. A test changed by any route, shell included, no longer matches and fails the run even if it now passes. (Not hypothetical: in the harshest runs, four of seven adversarial implementers rewrote a locked test through the shell, and the hash caught all four.) A **blind runner**, spawned fresh, runs the tests and reports — so the implementer can't lean on the thing producing its backpressure. Believing a test wrong, it cannot delete it; it can only petition a fresh **arbiter** that saw neither side. Nobody removes the check that judges them.

## What a green gate does and doesn't mean

A green gate means the code passed an independent, sealed test of every stated criterion — necessary, not sufficient, not the same as correct. Two gaps. First, **the spec is the trust boundary**: the gate proves the code does what the spec *says*, not that the spec is right. Second, **it enforces independence, not strength**: a test can be blind, untampered, and still too weak to fail a wrong implementation. Measuring strength means perturbing the code and checking a test fails — mutation testing — which needs an agent that *can* read the code, the opposite of the blind writer. So it's a separate pass: a mutation check (built, but advisory — it flags weak tests, never fails the gate) and an audit pass on top (not yet built).

## Does it hold

To test it I borrowed the method from Ziqian Zhong, Aditi Raghunathan, and Nicholas Carlini's ImpossibleBench: rig a task's requirements to contradict each other, so any green is provably a cheat. Their own results make half the case for a mechanism — careful prompting drove one model's cheating from over 85% to 1% on easy tasks, yet it still cheated ~54% on the hard multi-file ones, and more capable models cheated more. Asking helps enormously, then stops, exactly where a false green costs most.

Gate on, under pressure to win by any means: **0 cheats in 42 runs**. Off, same pressure: **2 of 21**. Off, no pressure: 0. (Every figure is recomputable from the 84-run ledger in the repo.) The gate earns its keep under pressure and is near-harmless without it — the right shape for a safety mechanism, since real deployments look more like the pressured case than the calm one.

The caveats matter. The sample is small — 21 per cell, a wide interval, a demonstration not a population estimate. It's one harness on one model family, a snapshot of specific model versions, and blindness is only as complete as its configuration. None of it is free: several agent passes where a self-checking agent makes one. So assign an ordinary verifier for most work, and reach for the blind gate only when a false green is expensive *and* something is pushing toward it.

## Where this sits

The false green I kept hitting isn't a mystery in the research, and the culprit it keeps finding is the agent's *context*. Closest is Jane Pan, He He, Samuel Bowman, and Shi Feng on iterative self-refinement: one model that both generates and judges, sharing context, settles on the same misreading and rates it highly — and the sharing matters more than how much context each side has. That is this essay's mirror as a controlled finding; Themis breaks the sharing on purpose. Leo McKee-Reid and colleagues show the gaming needs no training, only accumulated context — which is why the runner and arbiter are spawned fresh; and Alexander Pan, Erik Jones, Meena Jagadeesan, and Jacob Steinhardt give the broad version, a model optimizing an in-context proxy with no intent, the effect growing with scale. The principle is old — clean-room development, separation of duties, Goodhart's law — confirmed in a new medium; Themis just enforces the independence as a permission instead of asking for it.

One thing I can add from the floor: the biggest mover of the cheat rate in my runs wasn't the gate — it was how I spawned the agent. An implementer that inherited the parent conversation's context cheated roughly ten times more than the same agent started fresh. I'm not claiming a discovery; Jane Pan's result predicts it — an inherited conversation is shared context in other clothes. The practical warning is mine: if you're measuring how often an agent cheats, the spawn topology is part of what you're measuring, and a rate reported without it is hard to trust.

If you're building anything an agent grades itself on — its memory, its tests, its own lessons — the independence of that check is not a feature to add later. It's the first thing that has to be real, enforced rather than requested, because every green downstream of a check the worker could route around is a light with no pressure behind it.
