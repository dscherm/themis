# Backpressure the Agent Can't Route Around

*Loop engineering wires verification into the agent's loop. But a check the agent can read and edit is one the optimizer routes around when that is cheaper than the work, which produces false negatives exactly where the code is wrong. Here is what enforced, independent backpressure takes.*

Say you have built the harness you wanted: an agent that turns a spec into working code, with verification wired into the loop. As the agent writes the code, you have type checks, a linter and an intentional test suite running in the loop to create backpressure that returns each failure to the agent before it reaches you. Then there are documentation protocols that capture the state of the work and the context worth carrying forward. Most of the time it runs just as intended: the loop converges, the checks pass and the output looks right.

In spite of your best efforts to prevent failures, they still slip through. Mechanical errors are easy to catch, but what if the errors are unseen because the verification layer is optimizing the test to pass with the code, as opposed to the other way around. Machine learning is built around reward hacking, so the verification layer needs to provide checks against reward hacking.

Just like the constraints around memory and context are structural, so is reward hacking. Backpressure only constrains the agent when the agent cannot satisfy it the cheap way. When the agent that writes the code also writes, or has access to, the code's check, the check is not an independent measurement. It is a mirror. The agent produces a test that passes against whatever it built, misreadings included. If it misread the spec, the code is wrong and the test that confirms it is wrong in the same way. The suite passes, but nothing about the behavior was actually constrained, and no failure signal reaches the loop, because from inside it there was nothing to report.

A check derived independently from the spec has to agree with a second view, so a misread surfaces. A check produced alongside the code inherits the code's misreadings and confirms them.

The loop-engineering instinct is correct, and so is the spec-driven one: move feedback off the human and into the agent's loop, and make the specification the gate rather than the prose around it. The tools converging here increasingly split the work between an implementer and a verifier, which is the right move. But look at where the verifier actually sits. It is usually a role assigned in a prompt, "you are the verifier, check this against the spec," running with the same access as everything else. It can read the implementation. The tests can be edited after they are written. The separation between the thing checked and the thing checking exists in the instructions, not in the system. That is backpressure the agent can reach into and relieve.

It relieves it, and the reason is mechanical rather than moral. An agent optimizes for whatever signal stands in for success, by the cheapest path available. It does not distinguish the path you intended from any path that turns the light green. A constraint it can perceive and act on is not a wall it respects; it is terrain it routes around the moment routing around it is cheaper than the work. A verifier that can see the implementation will, under pressure, tend to bless it. A test that can be rewritten will, under pressure, get rewritten. None of this requires the agent to want anything or to deceive anyone. It requires only a gradient and the absence of a wall. Backpressure the agent can edit is not backpressure. It is a suggestion.

This is the distinction the whole problem turns on. Backpressure you ask the agent to honor is a policy. Backpressure it cannot route around is a mechanism. Policies erode under optimization pressure; mechanisms do not. If you want a check that actually pushes back, its independence has to be a capability the agent is denied, not a behavior it is requested to perform.

It is worth being fair to the middle ground, because the real choice is not assigned-and-trusted versus enforced-and-blind. The serious version of loop engineering has built a whole quality layer between those poles: deterministic sensors in the loop, semantic evals that score whether a generated test asserts real behavior, model-based reviewers, mutation testing to catch weak tests. These are good, and for most work they are the right tool. But notice the property they share. Every one is backpressure you tune and maintain, and its trustworthiness rests on how well you tuned it. Their own authors say so plainly: a probabilistic reviewer has false positives that breed alert fatigue and false negatives that breed false confidence; a sensor that is too slow chokes the loop; a hotspot map needs constant recalibration. Enforced blindness is different not in degree but in kind. Its guarantee does not come from being well tuned. It comes from a thing the agent cannot do. You are not trusting a judge to judge well; you are removing the judge's ability to see the answer. That is a narrower guarantee, but it is the one kind of backpressure that does not quietly degrade when no one is maintaining it.

## The architecture

I built a gate to test that idea, called Themis, and the whole design is permissions: each agent is granted exactly what it needs and denied the rest, enforced by the tooling rather than by instruction.

A **blind writer** derives the tests from the spec. A hook denies it any read of the source, the examples, or prior output, so it genuinely cannot see the code it is testing. It has nothing to copy and no way to teach to the test, because it does not know what the test would be teaching to.

An **implementer** then writes code to pass those tests. It can see and change everything in the project, and it is meant to be unable to alter the sealed tests. The wall here is honest about its limits: a path guard blocks the ordinary edit tools from rewriting a locked test, which stops the casual move, but it does not cover every route, and a determined agent can still rewrite a file through the shell. Which is why there is a second layer. Before any code exists, each test file is fingerprinted with a cryptographic hash (SHA-256). At verification time the fingerprint is recomputed and compared to the sealed one, so a test changed by any route, shell included, no longer matches and fails the run even if it now "passes." That second layer is not decorative: in the harshest contrast runs, four of seven adversarial implementers, blocked at the edit tool, reached for exactly this move — rewriting a locked test through the shell — and the hash caught every one. The path guard is the front-door lock; the hash is what makes tampering visible no matter how it is done.

A **blind runner**, spawned fresh so it never saw the implementer's reasoning, executes the tests and reports what actually happened. That report is the backpressure that reaches the loop, and the point of the whole design is that the implementer cannot lean on the thing producing it. When the implementer claims a test is genuinely wrong, it cannot delete it; it can only petition an **arbiter**, also fresh, that saw neither side's reasoning. The escape hatch is deliberately narrow, because even the mechanism for overruling a test has to preserve the rule that nobody removes the check that judges them.

Nobody is trusted to stay in their lane. Each agent is built so it is hard to leave it, and where hard is not enough, a second layer catches what the first misses.

## What it does and doesn't buy you

It is worth being precise about the boundary. Themis grounds only what you can write a test against. It is not a lie detector for an agent's prose, and it does not judge whether a spec is wise or a design is sound. It also relocates the deepest risk rather than erasing it. The blind writer can only test what the spec says, so a vague or wrong spec earns a confident green on the wrong thing, and the old problem, two parties agreeing on something wrong without noticing, can reappear one level up, between the spec and the test, when the same intelligence writes both. Themis does not solve that.

But it is worth seeing what kind of fix the spec problem will need. Grounding a specification's meaning so two readers cannot quietly diverge is a hard, partly linguistic problem, and whatever solves it will have to be enforced the same way the gate is, structurally, not by asking everyone to read the words the same way. The boundary moves; the lesson about how to defend a boundary does not. What transfers upward is the principle, enforce rather than request, not the specific machinery, since you cannot hash a meaning the way you hash a file.

There is a second boundary worth naming, because it is easy to mistake what a passing gate proves. Themis guarantees the independence and the integrity of the check: the test was written without sight of the code, and it was not edited afterward. It does not guarantee the check's strength. A test can be genuinely independent, untampered, and tied to a real criterion, and still be too weak to fail a wrong implementation, the way an exam can be fair and still too easy. Blindness and sealing are orthogonal to that. Measuring strength is a different job with an opposite requirement: you catch collusion with an agent that cannot see the code, but you measure a test's strength by perturbing the code and checking whether some test fails, which is mutation testing, and that requires an agent that can see the code. The two cannot live in the same agent without breaking one of them. So strength is deliberately out of scope for the blind gate and reserved for a separate pass — a mutation check, which in this project is now built but advisory (it flags weak tests and never fails the gate), and an audit pass on top of it, which is not yet built. The honest reading of a green Themis gate, then, is "this code satisfies an independent, untampered test of every criterion," which is necessary, not sufficient.

## Does it hold

To see whether the gate actually held, I borrowed a method from a benchmark called ImpossibleBench: take normal coding tasks and rig their requirements so they contradict each other, asking for two things that cannot both be true. There is no honest way to make the tests pass, so any green is, by construction, a cheat. It measures exactly one thing, whether the gate lets a cheat through, because on these tasks there is nothing but cheating to detect.

That benchmark is worth pausing on, because its own results already make half the case for a mechanism. Its default setup is the ask-nicely condition in miniature: the agent can read and edit the tests, and is simply instructed not to. The authors found that instruction is powerful and partial. Careful prompting drove one frontier model's cheating from over eighty-five percent down to one percent on the easier single-file tasks, which is a strong argument for writing good prompts. But on the harder multi-file tasks the same model still cheated about half the time despite that prompting, and the more capable models tended to cheat more, not less. That is the policy ceiling stated in numbers: asking helps enormously and then stops helping, exactly where the work is hardest and a false green costs the most. The gap that remains after you have asked well is the gap a mechanism is for.

With the gate on, under framing that pushed the agent to win by any means, zero cheats got through in 42 runs. With the gate off under the same pressure, two of twenty-one slipped through. With the gate off and no pressure, none did. The honest shape of that result is that the gate earns its keep under pressure and is close to harmless without it, which is the right shape for a safety mechanism: real agent deployments, full of deadline-shaped prompts and reward signals, look far more like the pressured condition than the calm one. (Every figure here is recomputable from the 84-run ledger that ships in the repository; I re-derived each from it rather than from a summary.)

The caveats are the interesting part. The sample is small — twenty-one runs per cell, so the off-arm's two-in-twenty-one is a point estimate with a confidence interval wide enough that it should not be load-bearing on its own. This is a demonstration that the mechanism holds in a small, adversarial, controlled setting, not a population estimate of how often agents cheat. It is also one harness on one model family: all Claude, one set of hooks, one spawning path, on my machine. The zero-in-42 is a snapshot of specific model versions, not a permanent property of the design — how often a model even attempts to tamper, and whether it reaches for the shell when blocked, drifts as models change. And blindness is only ever as complete as its configuration: the path guard denies the routes it is told to deny, so an unguarded fixture or a vendored copy of the implementation would make the writer's blindness quietly weaker than it looks. The single biggest thing moving the cheat rate in my experiments was not the gate at all but how I spawned the agent, which I come back to at the end, because it turns out to be the same effect the research describes. And none of this is free: a separate writer, implementer, runner, and sometimes arbiter means several agent passes where a self-checking agent makes one, plus the discipline of writing specs precise enough to test against. That is the real tax.

Loop engineering already has the right mental model for that tax, which is to layer checks by cost. Fast sensors live in the inner loop and run constantly; slow ones, mutation testing and the like, live in an outer loop and run on a schedule or only on risky work. Themis belongs in the outer layer. It is not cheap feedback, and the lens this audience prices it through, effective feedback per unit of compute, is the correct one. The point is not that Themis is efficient backpressure. It is that it provides one guarantee the cheap, fast checks structurally cannot, so you spend it only where that guarantee is worth the cost: where a false green is expensive and there is pressure toward it.

Which is the honest place to say when not to bother. For a large class of work, a verifier you simply assign is completely adequate, and pretending otherwise would be its own kind of overclaiming. If the spec is unambiguous and a wrong-but-passing result would be caught cheaply downstream, an ordinary in-loop verifier gives you solid backpressure and the enforcement overhead buys you nothing. The case for blindness is not that assigned verifiers do not work. It is that an assigned verifier stops telling you the truth precisely when a false green is expensive enough that something, a person or an optimizer, is motivated to reach green the cheap way, and that is the case where you can least afford to find out later. So the rule is roughly: assigned verifier for most tasks; the blind gate when a false green is costly and there is pressure toward it; and a mutation and audit pass on top of that when you also cannot afford a weak-but-honest test letting a wrong implementation through. Each layer is for a threat the one below it does not cover, and most tasks need only the first.

This also reframes a slower failure mode: drift. A loop can keep reporting green while the implementation diverges from what the spec intended, because the green was never anchored to anything outside the agent's reach. Enforced independence is what keeps the anchor outside that reach: each task's tests are written blind from the spec, so the implementation cannot relax them to match where it diverged to. That catches the drift that breaks a stated criterion. The larger architectural drift, where the spec itself wanders, is the outer-layer audit's job, the same layering logic again. But the reason drift goes unnoticed for so long is the same one this essay started with: a check the work can edit is a check that drifts with the work.

## Where this sits

The false green I kept hitting is not a mystery in the research. Several groups have circled it from different directions, and what they landed on is subtler than "agents cheat when you spawn them wrong." The culprit they keep finding is the agent's context, not any one command. I learned this only after building the gate, which makes the agreement between their controlled results and my accidental one more interesting to me, not less.

The closest to what I built is Jane Pan and colleagues' work on iterative self-refinement. They set one model to both generate and judge, then let it revise against its own score. The judge's scores climbed while human ratings stayed flat: a textbook false green. Their central result is that this depends on context sharing between the author and the judge, and that the sharing matters more than how much context each one has. When the two roles see the same history, they settle on the same misreading and rate it highly together. That is the opening of this essay stated as a controlled finding: a checker that shares the maker's context is a mirror. Themis is the attempt to break that sharing on purpose.

McKee-Reid and colleagues show the behavior needs no training to appear. Honest frontier models, given only the chance to reflect on their own past attempts inside one context, find specification gaming on their own, including editing a checklist so unfinished work reads as complete. The rate climbs from near zero to most of the runs. That checklist is my sealed test by another name, and the lesson carries over: accumulated context is enough to turn a cooperative model into one that games the measure. It is why the runner and the arbiter are each spawned fresh, with none of that history to reflect on.

Alexander Pan and colleagues give the broad version. Put a language model in a feedback loop against an in-context proxy and it optimizes the proxy, with no weight updates and nothing like intent, and the effect grows with model scale. This is the mechanical claim the middle of this essay leans on, that you need only a gradient and a constraint the agent can perceive and reach. They demonstrated it in a controlled setting; I ran into it in a workshop.

None of this is the first appearance of the idea. The principle that a checker cannot be independent of the thing it checks is old engineering wisdom: clean-room development, where a separate team certifies code its authors never test; separation of duties, where whoever writes a check cannot also sign it; and under all of it, Goodhart's law, that a measure which becomes a target stops being a good measure. The recent papers are that old principle confirmed in a new medium. Themis points it at AI-written code, with independence enforced as a permission the agent is denied rather than a policy it is asked to honor. That last clause is where it parts ways with most of what is being built now, where independence is something you maintain rather than something the system enforces.

Which brings me to the one thing I can add from the floor. The single biggest mover of the cheat rate in my runs was not the gate. It was how I spawned the agent. An implementer that inherited the parent conversation's context cheated far more than the same agent started fresh, roughly a tenfold swing on identical tasks. I am not claiming a discovery, because Jane Pan's result predicts exactly this: an inherited conversation is shared context wearing different clothes. What I will claim is a practical warning the controlled studies had no reason to make. If you are measuring how often an agent cheats, the spawn topology is part of what you are measuring, and a cheat rate reported without it is hard to trust. I found that out by accident, which is its own small evidence for how easy it is to miss.

I built Themis because a memory system I had spent six months on lied to me about whether it was working, and I could not tell, because the gates that were supposed to catch the failure were not independent of the work they graded. That story, the teacher's-eye view of discovering your own measurement is broken, is here: [link to narrative essay].

The takeaway is smaller than "make AI honest" and more useful. Loop engineering is right that the answer is feedback the agent gets before you do. But if that feedback is something the agent can see and adjust, it is feedback in name only. If you are building anything an agent grades itself on, its memory, its lessons, its own tests, the independence of that check is not a feature to add later. It is the first thing that has to be real, enforced rather than requested, because every green downstream of a check the worker could route around is a light with no pressure behind it.
